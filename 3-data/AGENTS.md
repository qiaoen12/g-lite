# 3-data — 数据集

## 放什么

采集来的、不能凭空重造的数据：爬取结果、API 导出、数据库快照、调研原始记录。

## 铁律：先写 DATASET.md，再开始采

没有数据字典的数据，半年后等于没有。审计会因为缺 `DATASET.md` 而失败。

```bash
new data research-career-jd     # 建骨架并打开 DATASET.md 模板
```

## 归属：数据集连着谁

数据集有两端。**采集端**是谁产出的，**应用端**是谁在用。两端都可能是零个、一个或多个：

- 一个采集器能产出多个数据集
- 一份数据能被多个项目引用
- 采了还没人用（只有采集端）
- 人工导入的（采集端是 `manual`）
- 两端皆空（这种不该存在，见下）

这是个多对多关系，**塞不进目录名**——名字只有一个位置。所以分三层：

| 层 | 承载什么 | 访问成本 | 完整性 |
| --- | --- | --- | --- |
| 目录名 | 主应用端 | `ls` 一眼 | 近似 |
| `DATASET.md` 的 frontmatter | 该数据集全部两端 | 读一个文件 | 精确 |
| `3-data/INDEX.md` | 全局双向关系 | 读一个文件 | 精确 |

第三层是重点：它让「某个项目要用的数据在哪」变成读一个固定文件，不用爬整棵树。
**它必须是生成的**，`new data --index` 从各 `DATASET.md` 的 frontmatter 汇总。
手写清单会漂移，这一点 backup 和 sync 各自已经证明过一次。

### frontmatter

每个 `DATASET.md` 顶部必填。`new data` 会生成骨架。

```yaml
---
dataset: research-career-jd
producers:
  - external: 浏览器 agent，按 pipeline/collect-prompt.md
consumers:
  - 4-know/research/career
primary_consumer: 4-know/research/career
---
```

`producers[]` 的 key 取 `code`（`1-code/<tool>`）、`pipeline`（本数据集的 `pipeline/<script>`）、
`manual`（人工下载导入）、`external`（外部工具或服务）。白名单在 `policy.yaml` 的
`link_declaration.producer_types`，写别的会被审计报出来。
多个数据集声明同一个采集端时，索引会按它反向聚合，一眼看出这个采集器产出了哪几份数据。

`primary_consumer` 决定目录名。多个应用端地位平等时填 `null`。

**列表只能写成 `[]` 或块式（每项一行、以 `-` 开头）。**有两种合法 YAML 会被这里的解析器
读成 0 项：行内列表 `consumers: [a, b]`，以及块式键下面写成映射——

```yaml
producers:
  code: collector      # ✗ 漏了 -，会被读成空
```

于是索引少一行而没有任何人知道。静默给错答案比拒绝解析危险得多，所以这两种都会被直接报出来。
**声明成块式却没有任何 `-` 项也算错**，空列表要显式写成 `[]`。

审计还查这四条自洽性，都是一眼能查、查了就不会说谎的：

| 判据 | 为什么 |
| --- | --- |
| `dataset` 字段存在，且等于所在目录名 | 这个字段没有任何程序在消费（索引用的是目录名）。不校验，它就是一行随时开始说谎的注释，而改目录名时最容易漏的恰好是它。缺失和写错一起查——只查「写了但不对」等于给「干脆不写」开后门 |
| `primary_consumer` 是 `consumers` 的成员 | 主应用端不在应用端列表里，说明有一处忘了改 |
| `producers` 每项形如 `<类型>: <说明>`，说明不能空 | 没有类型前缀，索引的反向聚合无从下手；说明为空，聚合表会多出一行空白主键 |
| `consumers` 指向的目录真实存在 | 死链的索引比没有索引更浪费时间。同 `new worktree` 对 `--path` 的处理：打错一个字，静默通过给你的是一个空结果 |

改完 frontmatter 要跑 `new data --index`。审计会**重新渲染一遍索引，与磁盘上那份逐字节比较**——
指纹只能证明声明没变，证明不了索引内容正确。索引过期或被手改，都会在这一项报出来。

### 目录命名

规则复用已有的 commit scope，不发明第二套词表：**scope 的点换成横线，再接数据集限定词**。

```
3-data/<scope 用横线>-<限定词>/
```

| 情况 | 名字取自 | 例 |
| --- | --- | --- |
| 单一应用端 | 应用端 scope | `research-career-jd` |
| 多应用端，有主次 | 主应用端 | 索引记全部 |
| 多应用端，地位平等 | `shared-` 前缀 | `shared-cn-holidays` |
| 只有采集端，还没人用 | 采集端 | `code-job-crawler-raw` |
| 只有应用端（人工导入） | 应用端 scope | producers 填 `manual` |
| 两端皆空 | — | **不该存在** |

地位平等时硬挑一个消费者当前缀是在说谎，`shared-` 才是准确信号。

两端皆空的数据集：没有采集端说明来路不明，没有应用端说明没人用。
它属于 `_inbox`，不属于这里。审计会报出来。

**只有一个数据集的时候也要带限定词。**第二个出现时再回头改名，所有引用都得跟着改，
而引用散落在 `4-know` 的正文、`pipeline/` 的路径和别人脑子里。

唯一的例外是 `example-*`。它是全工作区通用的示例约定（`example-topic`、`example-app`、
`example-dataset`），跨域一致比单域合规更重要。

## 目录形状

```
3-data/
├── INDEX.md            ← 生成物。双向查询表，new data --index 重算      进 git
└── <dataset>/
    ├── DATASET.md      ← 强制。frontmatter 声明两端；正文是数据字典     进 git
    ├── schema/         ← 字段定义、契约                                进 git
    ├── pipeline/       ← 采集与清洗脚本                                进 git
    ├── _raw/           ← 原始采集，可追加，不可改动已有（有哈希清单）    不进 git
    └── _out/           ← 清洗与派生，可由 pipeline 完全重建             不进 git
```

## 这个域是「部分进 git」

不是整域禁止。**不能进 git 的只有数据本体**——契约、字段定义和处理脚本都是小文本，而且它们才是「`_out` 能否重建」这个判断的前提。不版本化它们，可再生性就只是一句口头承诺。

`pipeline/` 以前建议放 `1-code/`。那样脚本和它处理的数据分居两域，改一个必须记得改另一个，而没有任何机制在检查这件事。现在留在数据集里，跟 `DATASET.md` 一起版本化。只有当采集器长成一个正经项目（有自己的依赖、测试、CLI）时才移去 `1-code/`。

## `_raw/` 是追加式的，不是冻结的

这是整个域唯一真正重要的约束。原始数据一旦被清洗脚本就地覆写，就再也回不去了——而重采往往不可能：接口改了、内容删了、被限流了。

准确的说法是**可以新增，不可以改动已有**：

| 动作 | 允许 |
| --- | :-: |
| 往 `_raw/` 追加新采集批次 | ✓ |
| 读 `_raw/` | ✓ |
| 修改、清洗、覆写 `_raw/` 里**已有**的文件 | ✗ |
| 删除 `_raw/` 里已有的文件 | ✗ |
| 把清洗结果写回 `_raw/` | ✗ |

清洗结果一律写 `_out/`。想不通该放哪的，就问一句：**这个文件删了，能不能靠脚本重新生成？** 能就是 `_out/`。

### 两道保障

```bash
# ① 权限位：只锁文件，目录保持可写（否则追加新批次会失败）
find 3-data/<dataset>/_raw -type f -exec chmod a-w {} +

# ② 哈希清单：权限位能被改回来，清单不能
new data --seal <dataset>          # 首次生成 _raw/MANIFEST.sha256
```

审计的 `raw_integrity` 会比对清单：

| 情况 | 结果 |
| --- | --- |
| 清单里没有的新文件 | `RAW_APPENDED` — 放行，写回清单 |
| 清单里有且哈希一致 | 通过 |
| 清单里有但哈希变了 | `RAW_MUTATED` — **硬失败** |
| 清单里有但文件不见了 | `RAW_DELETED` — **硬失败** |

这一项只在**深度档**（每周）跑，全量哈希是分钟级操作。

## 不放什么

| 不放 | 放哪里 |
| --- | --- |
| 采集器代码（已长成有依赖、测试、CLI 的正经项目） | `1-code/` |
| 分析结论、报告正文 | `4-know/` |
| 生成的图表、导出的 CSV | 就地 `_out/` |

## 策略

| 敏感度 | Git | 冷备 | 热同步 | 保留 |
| --- | --- | --- | --- | --- |
| 内部 | 部分：契约 + `schema/` + `pipeline/` | `_raw` 必须 / `_out` 不备 | **禁止** | 按 `DATASET.md` |
