# Git Guard

```text
refs/heads/*               staging 自己收到什么
refs/guard/github/heads/*  最近一次确认的 GitHub 世界
old-oid                    这次客户端声称基于什么
```

路径：

```text
git push
  → receive-pack wrapper（先 fetch GitHub → refs/guard/github）
  → git-receive-pack
  → pre-receive（只验证：contract/tip 读 snapshot，stale 则拒绝）
  → staging refs 更新
  → post-receive（一次 git push --atomic，每 ref --force-with-lease=<old>）
  → wrapper 按转发状态返回 0 / 非 0
```

fetch / claim 仍走 GitHub。主工作区不接线。安装：`new guard install`。

wrapper 在进入裸仓前，从发起 push 的 worktree git dir 读取 `new.task.issue`。
任务号不从分支名推导；未 bind 或 snapshot 缺契约时拒绝。
pre-receive 从 snapshot main 读 `contract.json` 与 `derived.lock`，逐条检查
main 之外的任务提交：message 共用 `check-commit-msg.sh`（保留 policy 的 wip /
autogenerated 例外），scope 与 hard-deny 共用 `task-paths.sh`。
重命名按删除与新增两端判断；历史越界后再 revert 也拒绝。仅删除 ref 不新增内容，
沿用 snapshot / CAS 门禁与 lease 转发。

main 的事后检测由 `.github/workflows/main-guard.yml` 调用 `main_guard.py`：
检查本次 push 的每条 first-parent 提交。PR 必须已合并到本仓 main，且
`merge_commit_sha` 精确相等；契约批准必须符合稳定 approve 的标题、任务编号和
`contract.json` / `contract.md` 路径。后者识别 approve 产物格式，不是调用者身份认证。
异常按完整 SHA 在全部状态的 Issue 中查重，创建带 `bug` 标签的 Issue 并返回失败；
API 读取、创建或结果确认失败也返回失败。人工编辑和已关闭的报告均保留。

workflow 串行查重与创建，使用 GitHub 的
[`queue: max`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency)
保留最多 100 个待处理运行；超过平台队列限制仍可能丢事件。
这只是事故检测：不阻止 main 更新、不自动 revert、不配置 required checks，
也不能抵御同一用户主动修改或绕开 Guard。真实 E2E 只允许在
`qiaoen12/g-lite-harness` 的 `e2e/*` 分支上替换事件目标运行。

本地定向夹具：`bash 0-meta/lib/new/guard.test.sh`；tripwire：
`python3 -B -m unittest discover -s 2-infra/git-guard -p '*_test.py'`。
