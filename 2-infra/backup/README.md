# backup

管什么：本工作区的 restic 冷备。**路径由 `0-meta/policy.yaml` 推导，不手写。**

## 三个脚本

| 脚本 | 干什么 |
| --- | --- |
| `scripts/gen-restic-args.sh` | `derived.lock` → `_out/files-from.txt` + `_out/exclude.txt` |
| `scripts/backup-cold.sh` | 跑备份。每次先重跑生成器，所以清单不可能过期 |
| `scripts/check-closure.sh` | 审计第 4 项：快照里的路径集合 vs 应备份集合 |
| `scripts/check-password.sh` | 审计 password_sources：机器取值、人恢复、纸质声明 |
| `scripts/install-unattended-password.sh` | 把 restic 口令装进 Keychain，供 launchd 用 |

`scripts/lib.sh` 是共享部分（读 lock、解析口令来源、rclone 限速）。

这几个文件里**没有**任何路径常量、仓库地址、保留期数字。换目的地、改保留期、
换口令库，都是改 `0-meta/policy.yaml` 然后 `new plan --apply`，不是回来改脚本。

## 日常

```bash
# 看清单。不碰仓库，不要口令，最适合确认「策略改动是否符合预期」
2-infra/backup/scripts/backup-cold.sh --list

# 试跑
2-infra/backup/scripts/backup-cold.sh

# 真跑（含保留期与 restic check）
2-infra/backup/scripts/backup-cold.sh --apply

# 换目的地
2-infra/backup/scripts/backup-cold.sh --dest cold-b2 --apply
```

## 口令

policy 的 `backup.password_source` 是一个**引用**，脚本把它翻译成取值命令，
交给 restic 的 `RESTIC_PASSWORD_COMMAND` 执行。口令不经过任何脚本的环境变量，
也不出现在 `ps` 输出里。支持的前缀：

```
op://<vault>/<item>/<field>      1Password CLI
keychain://<service>/<account>   macOS Keychain
bw://<item>                      Bitwarden CLI
pass://<name>                    pass
file://<path>                    文件（只在临时场景下用）
cmd://<任意命令>                  兜底
```

**灾难恢复用的口令必须存在于「你要防的那台机器」之外。**典型的死循环：
Mac 挂了 → 要恢复 → 需要口令 → 口令只在 Mac 上。所以人取值走口令库 + 纸质。

无人值守是另一件事：launchd 必须能在本机拿到某一个密钥，否则调度跑不起来。
本机只存 restic 仓库口令本身（Keychain），不存 Bitwarden 主密码。

| 字段 | 谁用 | 当前值 |
| --- | --- | --- |
| `password_source` | 机器（restic / launchd） | `keychain://restic-cold/restic-password` |
| `password_recovery` | 人（另一台机器、纸） | `bw://restic-cold` + `paper` |

交互装一次 Keychain 之后，日常备份不再需要 `BW_SESSION`：

```bash
cd /path/to/workspace
export BW_SESSION="$(bw unlock --raw)"
2-infra/backup/scripts/install-unattended-password.sh
unset BW_SESSION
2-infra/backup/scripts/backup-cold.sh --snapshots
```

纸质声明（不含口令正文）：`0-meta/audit/offline-copy.attestation`。
`new check` 每天查机器取值是否可达、人恢复是否含离机来源；纸质缺席只告警。

## 无人值守

`bw` 取值需要已解锁的 session，launchd 没有终端。所以机器取值改走 Keychain。

本机那份密钥的爆炸半径：

| 方案 | 本机存的是 | 爆炸半径 |
| --- | --- | --- |
| Keychain 存 restic 口令（当前） | 一个仓库口令 | 只有这个冷备仓库 |
| Keychain 存 Bitwarden 主密码 | 整个口令库的钥匙 | 所有凭据 |
| 不上调度，手动跑 | 无 | 无，但依赖人记得 |

装调度：

```bash
# edit absolute paths in the plist first
cp 2-infra/backup/launchd/com.g-lite.backup-cold.plist ~/Library/LaunchAgents/
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.g-lite.backup-cold.plist
```

每天 10:15 跑 `--apply`。Mac 合盖睡着会延后到醒来。备份运行日志在
`~/Library/Logs/g-lite-backup/`；launchd 的标准输出和错误分别在
`~/Library/Logs/com.g-lite.backup-cold.out.log` 与
`~/Library/Logs/com.g-lite.backup-cold.err.log`，因此首次 bootstrap
不依赖预先创建子目录。

## 三个刻意的设计

**清单不缓存。**`backup-cold.sh` 每次运行都重跑生成器。缓存一份清单就是给它
一个过期的机会，而清单过期正是 `backup_closure` 这项审计存在的理由。

**缺路径硬失败。**上一代对不存在的路径静默跳过，一个打错字的域名会安静地从
备份里消失。这里改成直接退出。唯一的例外是 `backup.external_paths`（worktree
根，用一个建一个），它允许缺席，但每次都打印。

**可再生目录按证据逐个判定，不按名字一刀切。**目录叫 `node_modules` 不等于
可以不备份——有锁文件才算可重建。一个「有 `node_modules` 但没有 `package.json`」
的目录谁也重建不出来，它恰恰是最需要进备份的那种。

## 上一代的三个坑

1. 路径清单手写（23 行），结果 `60-dev` / `80-data` / `80-research` 零副本，
   而审计报告写着「漂移 0 项」。**清单必须是算出来的。**
2. 无条件排除 `**/.git/**`。v2 不排除——worktree 的 `.git` 只是个指针文件，
   主仓库的 `.git` 进了备份，worktree 里的分支才恢复得出来。
3. 口令明文躺在 `70-infra/70-vps/credentials/secrets/vps-backup.env`，
   和它要保护的那台机器在一起。

## 巡检输出

`_out/`（生成的清单、日志索引）。保留名，自动不进备份、不进 git。
restic 运行日志在 `~/Library/Logs/g-lite-backup/`。

## 恢复演练

记录写 `0-meta/audit/restore-drill/YYYY-MM-DD.md`。审计检查最近一次是否超过
90 天。演练必须在另一台机器上、只用口令库里的口令完成——
**没演练过的备份等于没有备份。**
