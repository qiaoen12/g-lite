# 最小充分审查

仓库级 `zreview` 共同规则。Grok `/zreview` 与 Codex `$zreview` 读同一份。
不要用 Agent 私有 `verification` 配置替代本文件。

`zreview` 只读：不修改工作树、不 commit、不修代码。发现问题写 `Verdict=不通过`，交给 `zfix`。
不改变 `zmerge` 的机械合并门禁与显式触发语义。

开始语义审查前必须先通过最新 main 门禁（`git fetch origin main` 后 `git merge-base --is-ancestor origin/main HEAD`）。落后则立即停止，不写通过 Review，提示显式 `zsync`。本文件不负责同步。

## 目标

审查的目的是获得当前任务仍缺少的正确性证据，而不是追求尽可能多的检查。

默认采用“最小充分审查”。

涉及 GitHub Project、Issue、PR 等有状态远端流程时，最小充分审查须覆盖成功路径，以及会改变控制流或最终结果的关键读写失败、已有对象/重试和并发状态变化，并核对最终状态、持久化记录与用户提示一致。

修改共享 helper 时检查受同一不变量影响的调用点；复用既有远端对象时检查幂等性，并避免覆盖人工内容。

## 审查范围

优先选择能证明本次改动正确的最窄范围：

1. 当前 Issue 验收要求；
2. 当前 HEAD 相对基线的实际 diff；
3. 直接受影响的函数、脚本和调用点；
4. 直接受影响模块；
5. 必要时才扩大范围。

不要因为“保险”“完整性”或“反正很快”自动扩大范围。

## 不主动执行全量验证

默认不要主动运行：

- 全仓库 test；
- 全量 lint；
- 全量 typecheck；
- 完整 build。

只有以下情况才扩大到较大或全量范围：

- Issue 明确要求；
- 仓库门禁明确要求；
- 修改共享契约、公共接口、schema、构建配置或依赖；
- 局部验证不足以判断正确性；
- 局部失败有证据指向范围之外。

任务收尾本身不是运行全量测试的理由。进入 `zreview` 也不是。

## 已有验证证据

优先读取并复用 Checkpoint 中 `zdev` / `zfix` 已记录的验证证据。

同一代码状态下已经通过的验证不要重复运行。代码发生与该验证相关的新修改后，才重新运行。

不要为了“再确认一次”重复已经获得的证据。

## 审查发现问题时

发现失败或缺口时：

1. 优先分析第一个与本次修改相关的问题；
2. 判断当前 diff 是否能够解释问题；
3. 与本次改动无关的问题只记录并报告；
4. 不顺手修复范围外问题；
5. 不因为无关问题自动扩大任务范围。

`zreview` 本身不修改代码。

存在与当前任务相关的未解决问题时，Verdict 必须为“不通过”，交给 `zfix`。

## 补充验证

不要为了证明完成了工作而机械新增测试。

只有当新的定向验证能够覆盖本次实际新增或修复的行为，并且现有证据不足以支持 Review 结论时才执行。

避免：

- 重复已有断言；
- 验证语言或框架自身行为；
- 与本次改动无直接关系的覆盖率补齐。

## 输出控制

优先使用：

- 单测试；
- 定向测试文件；
- quiet / concise 模式；
- 只输出失败信息的选项。

避免为了获取少量信息，把大量无关测试日志送入上下文。

## 停止条件

当已经取得足以判断当前 HEAD 是否满足 Issue 验收的证据，并且没有新的相关失败信息时，停止审查。

不要继续扩大验证范围或增加工具调用。

## Review 结论

`Verdict=通过` 前必须确认：

- 当前 HEAD 满足 Issue 验收；
- 当前 diff 没有发现相关逻辑缺口；
- 必要的成功路径和关键失败路径已有证据；
- 共享 helper 的相关调用点已检查；
- 已有对象、重试和状态变化在适用时已检查；
- 没有与本次任务相关的已知未解决问题。

如果证据不足，Verdict 不得写“通过”。

## Review 报告

说明：

- 审查代码与调用点：实际审查了哪些代码和调用点；
- 复用证据：复用了哪些已有验证证据；
- 新增验证：新运行了哪些定向验证；
- 覆盖范围：验证覆盖了什么范围；
- 未执行的大范围验证：哪些较大范围验证没有执行；
- 剩余风险：存在什么剩余风险。

以上六项必须写入 Review 正文的 `### 最小充分审查` 段，字段名与 [`z-workflow.md`](../../../0-meta/templates/z-workflow.md) 模板一致。

不要在只做局部审查时声称“所有问题均已排除”。
