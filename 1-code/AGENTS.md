# 1-code — 自有代码

## 放什么

自己写的、自己维护的软件项目。**一个子目录 = 一个项目**，不是一个仓库。

## 不放什么

| 不放 | 放哪里 |
| --- | --- |
| clone 来的第三方项目 | `_vendor/` |
| 采集的数据 | `3-data/` |
| 运行产物、日志、导出 | 就地建 `_out/` |
| 任何明文密钥 | 1Password；仓库里放 `.env.tpl` |

## 起项目：不需要建仓库

```bash
new code my-app
cd 1-code/my-app
git add . && git commit -m "feat(code.my-app): 建项目骨架"
```

没有 `git init`，没有 `gh repo create`，没有 remote 配置。这个目录属于 本工作区根仓库。

在项目目录里可以直接跑 `git status` / `git add` / `git commit` / `git push`，不用回根目录——git 会自己往上找 `.git`。注意 `git add .` 只加当前目录，跨域改动要么分别 add，要么回根目录一次性提交。

## 为什么不是一人一个仓库

原设计是每个项目独立建 repo、独立 remote。放弃它不是因为 monorepo 更时髦，而是因为原设计把治理面切碎了：

`policy.yaml` 是唯一事实源，但它看不见任何一个子仓库的内部状态——有没有 push、有没有把 `.env` 提交进去、分支停在哪。几十个项目就是几十个 policy 管不到的盲区，而这套体系的全部价值就在于「规则能被机器验证」。

顺带消掉的成本：新项目不用先去 GitHub 建空 repo，不用记哪个 repo 对应哪个目录，`new check` 的副本数检查从几十次独立测量收敛成一次。

## 什么时候该独立出去

monorepo 是**默认**，不是永久禁止。不要求你在项目出生第一天就预测它的未来。

出现下面任一条时再拆：

- 准备开源
- 需要外部协作者
- 需要独立的 Issues / Release
- 独立 CI/CD 复杂到会干扰主线
- 需要不同的访问权限
- 其他系统需要直接 clone 它
- 生命周期已经明显脱离本工作区

拆的时候历史可以带走：

```bash
git filter-repo --path 1-code/foo --path-rename 1-code/foo/:
```

拆完必须做两件事，否则根仓库会一直报错：

1. 登记到 `0-meta/policy.yaml` 的 `git.standalone.repos`
2. 在根 `.gitignore` 里排除该路径

漏了第 2 步，内层 `.git` 会被根仓库记成 gitlink——外层 clone 出来是个空目录，而且 clone 的人不会收到任何警告。`new check` 的 git 卫生项会把这两件事一起卡住。

## 多个 AI 并行

不要让一个工作目录反复 `git switch`。给每个任务开独立 worktree：

```bash
new worktree reddit-v3 --path 1-code/reddit
new worktree discord-v2 --path 1-code/discord
```

每个 worktree 只暴露 `0-meta` 加你指定的路径，其余内容不会出现在磁盘上。完整流程见 [docs/07-git-工作流.md](../0-meta/docs/07-git-工作流.md)。

## git 远端不是备份

**git 只保护「已 commit 且已 push」的内容。**未提交的改动、未跟踪的文件，它一概不管。所以对代码而言，实际的 RPO 是「距上次 push 的时长」——两天没推，就可能丢两天。

因此这个域**同时进冷备份**。职责划分：

| | 管什么 | 不管什么 |
| --- | --- | --- |
| git 远端 | 版本历史、协作、回滚 | 你还没提交的那部分 |
| restic 冷备 | 灾难恢复，含工作区当前状态 | 版本历史（只有快照粒度） |

代价很小：`node_modules` `.venv` `target` `dist` 由可再生判定剥离，`_out` `_cache` 由保留名剥离，真正入备的只有源码正文和根 `.git`。

**worktree 是这条规则的一个缺口。**它在 仓库根的兄弟目录，默认不在备份根里。`policy.yaml` 的 `backup.external_paths` 已经把它显式收录，但在 restic 配置真正落地之前，worktree 里未提交的东西只有本机一份。

## 项目内部结构

```
my-app/
├── README.md          做什么、怎么跑、依赖什么
├── AGENTS.md          （可选）本项目的特殊规则
├── .env.tpl           ← 只放引用，形如 API_KEY=op://Private/my-app/key
├── .gitignore         ← 只写本项目特有的；通用规则在根 .gitignore
├── src/
├── tests/
└── _out/              ← 能机械重建的产物，自动不进备份不进 git
```

`runs/` `logs/` `output/` `tmp/` 统一改叫 `_out/`（`tmp/` 用 `_cache/`）。

**但 `_out/` 只能放能重建的东西。**判据是「删了能不能靠代码跑回来」，不是「看起来像不像产物」。人工定稿的文件、下载来的文件都不属于这里，落点见 [docs/02 的产物 vs 成果表](../0-meta/docs/02-代码项目.md)。

## 分组

超过 3 个强相关项目才允许加一层分组，且只允许一层：

```
1-code/account-reg/reg-factory/       ✓  成员 ≥3
1-code/account-reg/flowpilot/
1-code/account-reg/gujumpgate/

1-code/foo/bar/baz/                   ✗  超过一层
1-code/group-of-two/a/                ✗  成员 <3，应展平
```

## 起项目检查清单

- [ ] `new code <name>` 建骨架
- [ ] `README.md` 写清怎么跑
- [ ] 密钥写进 `.env.tpl`，用 `op run` 注入，不落盘
- [ ] 产物目录叫 `_out/`
- [ ] 有**真锁文件**（`package-lock.json` / `uv.lock` / `Cargo.lock`），不是 `requirements.txt`
- [ ] 有工具链版本声明（`.python-version` / `.node-version` / `.tool-versions`）
- [ ] 提交信息符合 `<type>(<scope>): <描述>`
- [ ] **没有** `1-code/<name>/.git`

## 策略

| 敏感度 | Git | 冷备 | 热同步 | 保留 |
| --- | --- | --- | --- | --- |
| 内部 | 根 monorepo 跟踪 | 是（源码与根 `.git`） | 是 | 永久 |
