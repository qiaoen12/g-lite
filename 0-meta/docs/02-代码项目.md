# 代码项目怎么起

> 一句话：**建目录就能开工。**项目属于 本工作区根仓库，不需要自己的 remote。
>
> 但根 remote **不是**备份——它只覆盖已提交且已推送的部分。这个域同时进冷备。

## 起新项目

```bash
new code my-app
cd 1-code/my-app
git add . && git commit -m "feat(code.my-app): 建项目骨架"
```

没有 `git init`，没有 `gh repo create`。`new code` 会生成：

```
my-app/
├── README.md      骨架已填好待补
├── .env.tpl       只放 op:// 引用
├── .gitignore     只写本项目特有的；通用规则在根 .gitignore
└── _out/          产物目录
```

在项目目录里可以直接跑 `git status` / `git add` / `git commit` / `git push`，git 会自己往上找根 `.git`。注意 `git add .` 只加当前目录——跨域改动要么分别 add，要么回根目录一次性提交。

## 为什么不是一人一个仓库

原设计是每个项目独立建 repo。放弃它的理由不是 monorepo 更好，而是原设计把治理面切碎了：`policy.yaml` 是唯一事实源，却看不见任何一个子仓库的内部状态——有没有 push、有没有把 `.env` 提交进去、分支停在哪。几十个项目就是几十个 policy 管不到的盲区。

顺带消掉的成本：不用先去 GitHub 建空 repo，不用记哪个 repo 对应哪个目录，副本数检查从几十次独立测量收敛成一次。

需要独立仓库时再拆，规则见 [07-git-工作流](07-git-工作流.md) 第十节。

## 根 remote 管什么，restic 管什么

| | 覆盖 | 不覆盖 |
| --- | --- | --- |
| git 远端 | 已 commit 且已 push 的内容、完整版本历史、协作 | **未提交的改动、未跟踪的文件** |
| restic 冷备 | 工作区当前状态，含未提交内容 | 版本历史（只有快照粒度） |

对代码来说，只有 git 的话实际 RPO 是「距上次 push 的时长」。两天没推，硬盘坏了就丢两天。所以两个都要，职责分开：**git 管版本历史与协作，restic 管灾难恢复。**

成本很低——真正入备的只有源码正文和根 `.git`，依赖目录和产物目录都会被自动剥离。

> 有个例外要记住：worktree 在 仓库根的兄弟目录，不在备份根里。里面未提交的东西副本数为零。见 [07-git-工作流](07-git-工作流.md) 第九节。

## clone 别人的仓库

```bash
new vendor https://github.com/foo/bar     # 进 _vendor/，自动登记 VENDOR.md
```

`_vendor/` 下的东西自带上游 `.git`，根仓库不跟踪它们（只跟踪 `VENDOR.md`）。

后来发现自己改出了有价值的东西，两条路：

```bash
cd _vendor/bar
git log --author="$(git config user.email)" --oneline | wc -l    # >0 就该处理
```

| 情况 | 做法 |
| --- | --- |
| 只是自用改动，不打算回馈上游 | `rm -rf _vendor/bar/.git` 后 `mv _vendor/bar 1-code/bar`，并入 monorepo |
| 要跟上游同步、要提 PR | `gh repo fork` 保留独立仓库，登记到 `git.standalone.repos` 并在根 `.gitignore` 排除 |

**fork 是少数必须保持独立仓库的情况**——放进 monorepo 就没法 `git fetch upstream`，也没法向上游提 PR。

## _out/ 的准确定义

`_out/` 的策略是**不备份、不同步、随时可删**。所以进去的东西必须满足一条：

> 由「已备份的输入 + 已版本化的代码 + 已声明的命令」，能**机械重新生成**。

判据是能不能重建，**不是**看起来像不像产物。「报告」「导出」这类词太宽，会把无法重建的最终成果吸进一个随时可删的桶里。

### 产物 vs 成果

| 东西 | 能机械重建吗 | 落点 |
| --- | :-: | --- |
| 脚本跑出的统计表、清洗结果 | ✓ | `_out/` |
| 脚本生成的图表 | ✓ | `_out/` |
| 构建产物、编译输出 | ✓ | `_out/` 或 `dist/` |
| 测试覆盖率报告 | ✓ | `_out/` |
| **人工改了两小时的 PPT** | ✗ | `4-know/writing/` + 附件进 `4-know/_files/` |
| **客户签署的 PDF** | ✗ | `5-record/合同/` |
| **已发布、要留存原版的研报** | ✗ | `4-know/writing/` 或 `_archive/` |
| **下载来的第三方文件** | ✗ | `_inbox/` 或 `3-data/<name>/_raw/` |

最后一行以前写错过——下载的文件不是你的代码产出的，重建不了，放 `_out/` 等于随时可能蒸发。

### 改名对照

| 别用 | 用 | 前提 |
| --- | --- | --- |
| `runs/` `logs/` `output/` `outputs/` | `_out/` | 能重建 |
| `reports/` `exports/` | `_out/` | **仅当**是脚本生成的 |
| `downloads/` | `_inbox/` 或 `_raw/` | 下载物不可重建 |
| `tmp/` `temp/` | `_cache/` | — |

### 一条硬要求

**`_out/` 必须能说出重建命令。**写在 `README.md`、`DATASET.md` 或 `Makefile` 任一处即可，审计会告警缺失。

说不出重建命令的目录就不是 `_out/`——这条规则的全部意义在于逼你在删掉它之前先确认它真的能回来。

## 依赖目录不用改名，但要有真锁文件

`node_modules` `.venv` `target` `dist` `.next` 保持原样。是否可再生看有没有**锁文件**——注意锁文件和依赖声明不是一回事：

```
requests>=2.0        ← requirements.txt 里这么写，半年后装出来的不是同一套
numpy
```

准确的公式是：

> 可重建 = **依赖版本被钉死** + **工具链版本已知** + **构建命令已知**

### 三档判定

| 档 | 证据 | 备份 | 审计 |
| --- | --- | :-: | --- |
| 强 | `package-lock.json` `pnpm-lock.yaml` `uv.lock` `poetry.lock` `Cargo.lock` `Pipfile.lock` `go.sum` | 不备 | 通过 |
| 弱 | `package.json` `pyproject.toml` `requirements.txt`（未全钉死）`Pipfile` | 不备 | **告警**，提示补锁文件 |
| 无 | 什么都没有 | **进备份** | 告警 |

`requirements.txt` 里每一行都用 `==` 钉死时，自动升级为强证据。

### 别忘了工具链

锁住依赖但没锁 Python / Node 版本，换台机器照样重建不出来。补一个：

```bash
echo "3.12.4" > .python-version      # 或 .node-version / .tool-versions
```

审计对缺失只告警不阻断，但这是「能重建」和「以为能重建」的分界线。

### 重建命令对照

| 锁文件 | 重建 |
| --- | --- |
| `package-lock.json` | `npm ci` |
| `pnpm-lock.yaml` | `pnpm install --frozen-lockfile` |
| `uv.lock` | `uv sync --frozen` |
| `poetry.lock` | `poetry install --sync` |
| `Cargo.lock` | `cargo build --locked` |

### 构建产物是另一套逻辑

`dist/` `build/` `.next/` 这类目录能不能重建，取决于**源码是否已提交并推送**，跟锁文件无关。这一条在 `1-code` 改为进冷备之后才真正成立——在那之前源码本身就没有第二副本，谈不上「靠源码重建产物」。

## 分组规则

```
1-code/account-reg/{reg-factory,flowpilot,gujumpgate}/     ✓ 成员 ≥3，只有一层
1-code/a/b/c/                                              ✗ 超过一层
1-code/pair/{x,y}/                                         ✗ 成员 <3，应展平
```

## 检查清单

- [ ] **没有** `1-code/<name>/.git`
- [ ] `README.md` 写清怎么跑、依赖什么
- [ ] 密钥走 `.env.tpl` + `op run`
- [ ] 产物在 `_out/`，且 `README.md` 里写了重建命令
- [ ] 有**真锁文件**（不是裸 `requirements.txt`）
- [ ] 有工具链版本声明
- [ ] 提交信息符合 `<type>(<scope>): <描述>`
- [ ] `new check` 无红项
