# 数据集怎么建

> 一句话：**先写 DATASET.md 再开始采；`_raw/` 可以追加，不能改动已有。**

## 建一个

名字不是随便取的。**先想清楚这份数据给谁用**——目录名取自主应用端的 commit scope，
点换成横线，后面接一个数据集限定词：

```bash
new data research-llm-reddit          # 给 4-know/research/llm 用的 reddit 数据
```

生成：

```
3-data/research-llm-reddit/
├── DATASET.md      ← 先填这个，顶部 frontmatter 声明这份数据连着谁
├── _raw/           ← 原始采集，追加式
├── _out/           ← 清洗与派生，可重建
└── pipeline/       ← 处理脚本
```

**只有一个数据集的时候也要带限定词。**第二个出现时再回头改名，所有引用都得跟着改，
而引用散落在 `4-know` 的正文、`pipeline/` 的路径和别人脑子里。

多应用端、只有采集端、地位平等用 `shared-` 前缀这几种情况，见
[`3-data/AGENTS.md`](../../3-data/AGENTS.md) 的「目录命名」。

## 归属：这份数据连着谁

目录名只有一个位置，装不下多对多关系（一个采集器能产出多份数据，一份数据能被多个项目引用）。
所以目录名承载导航，`DATASET.md` 顶部的 frontmatter 才是事实源：

```yaml
---
dataset: research-llm-reddit
producers:
  - pipeline: pipeline/fetch.py，Reddit 官方 API 增量拉取
consumers:
  - 4-know/research/llm
primary_consumer: 4-know/research/llm
---
```

`3-data/INDEX.md` 由这些 frontmatter 生成，回答反向问题「我在做 X，该用哪份数据」：

```bash
new data --index        # 改完 frontmatter 就跑一次
```

写的时候有三类东西会被审计报出来：

| 会被报出来 | 为什么 |
| --- | --- |
| 会被读成空的写法 | 行内列表 `consumers: [a, b]`、块式键下面写成映射（漏了 `-`）、声明成块式却一项都没有。三种都是合法 YAML 但会被读成 0 项，**静默给错答案比拒绝解析危险得多**，所以空列表必须显式写成 `[]` |
| 采集端类型不在 `code` / `pipeline` / `manual` / `external` 里，或没写说明 | 白名单在 `policy.yaml` 的 `link_declaration.producer_types`；说明为空会让索引的聚合表出现空白主键 |
| 声明自相矛盾 | `dataset` 缺失或与目录名不一致、`primary_consumer` 不在 `consumers` 里、`consumers` 指向的目录不存在 |

`INDEX.md` **不要手改**。审计会重新渲染一份与它逐字节比较，手改一定会被发现。

## _raw/ 是追加式的，这是唯一真正重要的约束

原始数据被清洗脚本就地覆写之后，再也回不去了。而重采往往不可能——接口改了、内容删了、限流了。

注意准确的说法不是「只读」。像 Reddit、Discord 这种持续采集的数据集，天天都要往里加新批次。要禁的是**改动已有记录**：

| 动作 | 允许 |
| --- | :-: |
| 往 `_raw/` 追加新批次 | ✓ |
| 读 `_raw/` | ✓ |
| 修改 / 清洗 / 覆写 `_raw/` 里**已有**的文件 | ✗ |
| 删除 `_raw/` 里已有的文件 | ✗ |
| 把清洗结果写回 `_raw/` | ✗ |

判断某个文件该放哪，问一句：**这个文件删了，能不能靠 pipeline 重新生成？** 能就是 `_out/`。

## 两道保障

### ① 权限位（防手滑）

```bash
find 3-data/research-llm-reddit/_raw -type f -exec chmod a-w {} +
```

**注意不要写成 `chmod -R a-w _raw/`。**那会连目录的写位一起去掉，而目录写位控制的是「能不能在里面新建文件」——加了之后追加新批次会直接失败。只锁文件，目录保持可写。

### ② 哈希清单（防悄悄改）

权限位能被 `chmod` 改回来，改完没人知道。清单不行：

```bash
new data --seal research-llm-reddit     # 生成 _raw/MANIFEST.sha256
```

审计的 `raw_integrity` 比对清单：

| 情况 | 结果 |
| --- | --- |
| 清单里没有的新文件 | `RAW_APPENDED` — 放行，并写回清单 |
| 清单里有，哈希一致 | 通过 |
| 清单里有，哈希变了 | `RAW_MUTATED` — **硬失败** |
| 清单里有，文件不见了 | `RAW_DELETED` — **硬失败** |

这一步把「原始数据不可变」从文档纪律变成了机器能验证的事实。

因为要算全量哈希（分钟级），它只在**深度档**跑，每周一次，不进 pre-commit。

## DATASET.md 必填什么

审计会因为缺这个文件而失败。它回答的是半年后你自己会问的问题：

| 字段 | 例子 |
| --- | --- |
| 这是什么 | r/LocalLLaMA 2024-01 起的帖子与评论 |
| 采集方式 | Reddit API，`pipeline/fetch.py`，每日增量 |
| 采集窗口 | 2026-03-01 起，至今 |
| 有没有中断 | 2026-05-12 至 05-19 因限流缺失 |
| 每列是什么 | 逐字段说明 + 单位 |
| 唯一键 | `post_id` |
| 已知问题 | 删除的帖子会留空壳；作者名可能已改 |
| 能不能重采 | 不能，历史帖子会被删 |
| 保留多久 | 永久（不可重采） |

**「能不能重采」和「保留多久」决定备份策略，必须填。**

正文之外，顶部 frontmatter 的两端声明也是必填的，见上面的「归属」。

## 采集器代码放哪

| 情况 | 放哪 |
| --- | --- |
| 抓取与清洗脚本 | `pipeline/`，**跟数据集一起进 git** |
| 已长成正经项目（有依赖、测试、CLI） | `1-code/`，`DATASET.md` 里注明入口 |

`pipeline/` 留在数据集里是有意的。它和它处理的数据在同一个目录、同一个 commit，改一个必然看见另一个。以前建议默认放 `1-code/`，那样两者分居两域，而没有任何机制在检查它们是否还对得上。

## 分析结论放哪

**不放这里。**图表、CSV 导出放 `_out/`；结论、报告正文放 `4-know/`。

## 策略

| 项 | 值 |
| --- | --- |
| `_raw/` | 必须备份，禁止同步，**不进 git**，追加式（`MANIFEST.sha256` 校验） |
| `_out/` | 不备份，不进 git（可由 pipeline 重建） |
| `DATASET.md` `schema/` `pipeline/` | **进 git** |
| 整个域 | 禁止同步 |

这个域是「部分进 git」，不是整域禁止。不能进 git 的只有数据本体——契约和代码是小文本，而且它们才是「`_out` 能否重建」这个判断的前提。不版本化它们，可再生性就只是一句口头承诺。

## 检查清单

- [ ] `DATASET.md` 已填完，特别是「能不能重采」
- [ ] frontmatter 的 `producers` / `consumers` 是真声明，不是模板占位符
- [ ] 跑过 `new data --index`，`3-data/INDEX.md` 里能看到这个数据集
- [ ] `_raw/` 里的**文件**已加只读位（目录仍可写）
- [ ] `_raw/MANIFEST.sha256` 已生成
- [ ] pipeline 能从 `_raw/` 完整重建 `_out/`
- [ ] `DATASET.md` 里写了 `_out/` 的重建命令
- [ ] 目录名是小写英文，且带主应用端 scope 前缀与数据集限定词
- [ ] `git status` 里没有 `_raw/` 或 `_out/` 的文件
