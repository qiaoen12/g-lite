# 权限边界

> 一句话：**`AGENTS.md` 管行为，权限系统管能力。两者不能互相替代。**

## 问题

工作区里所有关于「AI 该读什么」的约定，写在 `AGENTS.md` 里。它对配合的 agent 有效，对下面这些无效：

| 场景 | `AGENTS.md` 挡得住吗 |
| --- | :-: |
| Agent 按规范先读最近的 `AGENTS.md` | ✓ |
| 你直接在 `~/` 打开编辑器，索引整棵树 | ✗ |
| 某个 npm 包的 postinstall 脚本 | ✗ |
| 第三方 CLI 工具、MCP server | ✗ |
| 被诱导忽略指令的 agent | ✗ |

**FileVault 也不解决这件事。**它加密的是关机状态下的磁盘，防的是硬盘被拿走。任何以你的用户身份正在运行的进程，读到的都是已解密的内容。

## 三层，只有第三层是边界

| 层 | 机制 | 强度 | 挡不住什么 |
| --- | --- | --- | --- |
| 1 声明 | `policy.yaml` 的 `ai_access` | 零 | 一切。它只是意图的事实源 |
| 2 工具 | 每个工具各自的配置文件（见下） | 中 | 不认这些文件的工具 |
| 3 系统 | 独立加密卷，默认不挂载 | 高 | 你自己挂载的那段时间 |

### Layer 1 — 声明

```yaml
ai_access:
  layer_1_declaration:
    0-meta:   read
    1-code:   read-write
    2-infra:  read-write
    3-data:   read
    4-know:   read-write
    5-record: deny
    _inbox:   read
    _vendor:  read
```

它的作用是给下面两层提供唯一的生成源，避免「ignore 文件和文档说的不一样」。

### Layer 2 — 工具

**没有「通用 AI 访问控制标准」这种东西。**每个工具只认自己的配置文件，所以这一层不是一个文件，是一组 adapter。`.cursorignore` 不是「本工作区的 AI 权限系统」，它是这套策略针对 Cursor 的一个适配器。

| 工具 | 适配文件 | 能强制吗 | 说明 |
| --- | --- | :-: | --- |
| Cursor | `.cursorignore` | ✓ | Cursor 自己拒绝读，agent 绕不过 |
| Claude Code | `.claude/settings.json` 的 `permissions.deny` | ✓ | deny 优先于任何 allow；同时约束 Bash 里的 `cat`/`head`/`tail` |
| JetBrains AI 等 | `.aiignore` | ✓ | 非正式约定，认的工具不多 |
| Codex / WorkBuddy | `AGENTS.md` | ✗ | 只有行为规范，没有路径级 deny |

最后一行是这套体系当前最大的敞口：**对 Codex 和 WorkBuddy 而言，layer 2 是空的**，实际保护等级直接掉回 layer 1（也就是零）。在 layer 3 落地之前不要假装它不存在。

三个共同的限制，任何 adapter 都挡不住：

- agent 自己写一个脚本去 `open()` 文件
- 以你的用户身份运行的任何其他进程
- 备份、同步、索引这类不看这些文件的工具

**为什么 `.cursorignore` 要手动拷：**Cursor 不允许 agent 写入它。一个能修改自己访问控制文件的 agent 等于没有访问控制。这条限制本身就说明了 layer 2 和 layer 1 的区别——前者是工具在执行，后者是文档在约定。代价是 `new setup` 只能检查它、不能代劳。

```bash
cp 0-meta/templates/cursorignore.tpl .cursorignore    # 必须你自己跑
git check-ignore -v .cursorignore                     # 无输出 = 没被忽略，直接 git add
git add .cursorignore
```

`git add` **不需要 `-f`**。文件名以点开头不会让 git 忽略它——只有 `.gitignore`、全局 ignore 或 `.git/info/exclude` 命中时才需要。「每次都得加 `-f`」通常说明规则和意图不一致，那时候该改 `.gitignore`，不是永久靠 `-f` 绕。

审计只检查 `enforced: true` 的 adapter，清单从 `derived.lock` 的 `ai_access.adapter_files` 读。**加一个新工具是改 `policy.yaml`，不是改脚本。**

### Layer 3 — 系统

把 `5-record` 挪出普通文件系统：

```bash
# 建一个 10 GB 的加密卷（稀疏，实际占用按需增长）
hdiutil create -size 10g -type SPARSEBUNDLE -fs APFS \
  -encryption AES-256 -stdinpass \
  -volname records ~/Vaults/records.sparsebundle

# 用的时候挂载
hdiutil attach ~/Vaults/records.sparsebundle -mountpoint ~/<workspace>/5-record

# 用完卸载 —— 这才是关键动作
hdiutil detach ~/<workspace>/5-record
```

口令存 1Password，**不要**勾选钥匙串自动解锁——自动挂载等于没有第三层。

**为什么这比 allowlist 强：**allowlist 要枚举「谁不许读」，而未挂载的卷不需要枚举任何东西。这与密钥策略是同一个思想的第二次应用——让最高敏感度的东西离开这个命名空间，而不是在命名空间里给它贴标签。

## 备份怎么办

加密卷挂载期间，`5-record` 是一个正常目录，restic 照常备份。所以：

- **备份任务必须在挂载状态下跑**，否则备份的是一个空挂载点
- 审计的 `backup_closure` 会因为「应备份集合里有 `5-record` 但快照里没有」而失败，正好起到提醒作用
- 或者反过来：把加密卷本体（`.sparsebundle`）作为一个整体备份

推荐前者。备份 sparsebundle 本体会让 restic 的去重失效（band 文件是加密的，内容一变整块变）。

## 一句提醒

第三层做完之前，不要把「`5-record` 是安全的」当成既成事实。现在它的实际保护等级是 layer 2：**认这个文件的工具会绕开它，不认的不会。**
