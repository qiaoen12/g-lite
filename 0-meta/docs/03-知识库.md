# 知识库怎么写

> 一句话：**不靠文件夹分类，靠 frontmatter 属性。**目录只管物理存放，视图靠查询生成。

## 为什么不用文件夹分类

一篇资料可以同时属于「方法论」「Cloudflare」「某项目」「待读」。文件夹强迫你选一个，选完之后从另一个角度就找不到了。

属性（`topic: [a, b, c]`）是多值的，这才是 Notion 数据库真正有用的地方。用本地 markdown 一样能拿到，还多了可 grep、可 git、agent 能直接读三个好处。

## 建一篇

```bash
new note   cf-waf-rules      # 自己的想法、总结
new source arxiv-2401-12345  # 外部资料摘录
new adr    use-sqlite        # 技术决策
new rb     restart-gateway   # 操作手册
```

## frontmatter 字段

```yaml
---
id: cf-waf-rules            # 稳定标识符，建立后永不改
type: decision              # note | source | decision | runbook
status: active              # draft | active | archived
topic: [infra, cloudflare]  # 多值。这是替代文件夹的关键
scope:                      # type=decision 时必填，见下一节
  - infra.gateway
primary_scope: infra.gateway
confidence: medium          # high | medium | low
created: 2026-08-26
review: 2027-02-26          # 复审日期，过期由审计报出
---
```

| 字段 | 为什么需要 |
| --- | --- |
| `id` | 文件改名、换目录、内容重写，引用都不断。链接靠它不靠路径 |
| `topic` | 多值归属。文件夹做不到 |
| `source` | 半年后你会想知道这段话是谁说的 |
| `scope` | 决策作用于哪几块。词表与提交语言共用，被索引消费 |
| `confidence` | 区分"我确认过"和"看到有人这么说" |
| `review` | 防止知识库腐烂。技术类 6 个月，方法论类 2 年 |

`topic` 与 `scope` 不重叠：`topic` 回答「讲的是什么主题」，自由造词；`scope` 回答「改的是哪块」，必须落在已有词表里。上面那份 yaml 里两个字段都写了，是为了展示形状——`type: note` 的文件不用写 `scope`。

## 七个目录按"是什么"分

| 目录 | 放什么 |
| --- | --- |
| `note/` | 自己的想法、总结、经验 |
| `source/` | 外部资料摘录 |
| `decision/` | 技术选型、方案决策（ADR）。全部 ADR 都在这里，不按项目分散，见下节 |
| `runbook/` | 操作手册、SOP |
| `research/<topic>/` | 成体系的调研 |
| `writing/` | 对外长文草稿 |
| `report/` | 成篇的自用技术报告与复盘，单文件 HTML，命名 `YYYY-MM-DD-<主题>.html` |
| `_files/` | PDF、图片附件，不进 git |

注意这是按**文档种类**分，不是按**主题**分。主题在 `topic` 字段里。

## 决策记录：四层溯源里的第三层

先说清楚 ADR 回答哪个问题，因为剩下三个问题各有各的答案，写错地方就等于没写。

| 想知道 | 去哪里 |
| --- | --- |
| 现在的规则是什么 | `policy.yaml` / `README.md` / runbook |
| **为什么这样规定** | **ADR** |
| 当时具体怎么变化 | `git log -- <ADR 或相关路径>` |
| 后来为什么改方向 | 新 ADR 的 `supersedes` |

git 那两层回答的都是「做了什么」。ADR 回答的是「当时为什么选这个、比较过什么、接受了什么代价、什么情况下要重新评估」——这四件事在 git 里一条都查不到。

### 什么时候写、怎么改

- 只有**难以逆转**、影响安全 / 恢复 / 接口、或者未来很可能再次争论的选择才写。不是每个技术选择都要写。
- `draft` 只存在于工作分支，合入 `main` 前变成 `active`。**`main` 本身就是「已接受决定」的边界**，所以受控块不需要过滤草案。
- 改完 `scope` 跑一次 `new adr --index`。
- 修正文案、补证据、补**实际观察到的后果**，直接改原 ADR——git 负责保留旧版本，那一节三个月后最值钱。
- 只有**决定本身改变**时才新建 ADR，用 `supersedes` 指向旧记录。旧记录留着，不删。
- `status` 与 `confidence` 回答不同的事：前者是「现在算不算数」，后者是「对当初的理由有多大把握」。一个已经在跑但当初没留比较记录的决定，正确写法是 `active` + `low`。
- `review` 只给容易随环境变化的决策填。稳定的基础决策靠正文的「什么情况下重新考虑」做事件驱动的重评，不必为了形式定期复审；缺 `review` 是合法的，审计会计入「跳过」。

## 级别与两份索引

ADR 还有个额外问题：它天生跨域。一条决策常同时动 `policy.yaml`、脚本、文档和某个项目，而一个项目的决策也不止一条。这是多对多，**塞不进目录名**——和数据集两端是同一个形状的问题，所以用同一个解法。

```bash
new adr use-sqlite      # 建骨架，scope / primary_scope 预填成空声明
# 填完 scope，然后：
new adr --index         # 重算总索引 + 刷新各目录受控块
```

### 级别从 scope 形状推，不是单独的字段

| `primary_scope` 形状 | 级别 | 例 |
| --- | --- | --- |
| 裸 domain | 体系级，声明粒度是整个域 | `repo`、`meta`、`data` |
| `<domain>.<unit>` | 单元级，一个项目 / 基础设施单元 / 数据集 | `infra.backup`、`code.my-app` |
| `<domain>.<unit>.<member>` | 成员级 | `code.group.member` |

**「体系级」说的是声明粒度，不是影响面。**裸 `repo` / `meta` 确实约束整个工作区，但裸 `data` / `vendor` / `inbox` / `record` 只约束自己那个域。级别回答「声明得多粗」，影响面要读正文。

词表就是提交语言那一套，不发明第二份——它已经从目录树派生并被 commit-msg 钩子验证。刻意不引入 `level: high|mid|low`：那会立刻与 scope 分叉，而且「高」是主观的，声明粒度是可判定的。

从目录树派生的 scope 按实际路径深度定级，**不能只数点号**：合法目录名本身可以含点，`code.foo.bar` 既可能是单元 `foo.bar`，也可能是分组 `foo` 的成员 `bar`；工具会保留枚举时的真实路径，两种同时存在就拒绝。四个语义别名（`meta.policy` `meta.agents` `meta.new` `meta.hooks`）是例外——它们绑定文件而非目录层级，级别按点号段数定，所以 `meta.policy` 解析到的目录是 `0-meta`（与裸 `meta` 同深度）却算单元级。

`primary_scope` 为 `null`（多个 scope 地位平等）时，级别取 `scope` 里最浅的那一项——影响面按最宽的算。

### 两份索引，回答两个不同的问题

| 落点 | 回答 | 谁在读 |
| --- | --- | --- |
| [`0-meta/DECISIONS.md`](../DECISIONS.md) | 这套系统怎么演进成现在这样 | 想通盘了解的人，按级别分组 + 时间线 |
| 各目录 `AGENTS.md` / `README.md` 的受控块 | 我在改这块，它背后有哪些决策 | 正在那个目录里干活的人或 agent |

第二份是真缺口。根 `AGENTS.md` 定的阅读顺序是「目标目录最近的 `AGENTS.md` → 目录内 `README.md` → `policy.yaml`」，`4-know/decision/` 不在这条链的任何一环——在 `2-infra/backup` 里改备份脚本的人永远不会知道 `restic-cold-backup` 存在。

受控块的落点规则：scope 对应目录有 `AGENTS.md` 就写它，否则写 `README.md`；两者都没有就往上找最近的祖先目录（不凭一条声明在项目里凭空造文件）。回退是必需的而不是兜底——`3-data/example-dataset`、`4-know/note`、`4-know/research/career` 这类目录都没有自己的 `AGENTS.md`，不回退就等于对多数单元级 scope 静默失效。

回退方向与根 `AGENTS.md` 的阅读顺序一致。深度取决于目标目录：八个域目录都有 `AGENTS.md`，所以域内 scope 最多退到域目录；但 `research.<topic>` 走两层（`4-know/research/<topic>` → `4-know/research` → `4-know`）。别名 `meta.hooks` 绑定根目录下的 `.pre-commit-config.yaml`，落点直接是根 `AGENTS.md`——那是每次都加载的规则文件，写进去之前先确认这条决策真的是仓库级的。

`ai_access` 声明为 `deny` 的目录例外：不写、不 stat、不 grep。`record` 是合法 scope 且映射到 `5-record`，这类 scope 会被报成告警，只在总索引里可查。

索引里的链接用文件的实际相对路径，不用 `id` 拼——`id` 稳定的含义是「改名不断引用」，靠 id 拼路径恰好会在改名时断掉，而且断得静默。路径会做百分号编码：`4-know` 的文件名是自由的，而决策记录爱用 `为什么不用 borg?.md`、`选 restic (而不是 borg).md` 这种写法，其中 `?` 会被当查询串、`)` 直接截断链接语法。编码覆盖 `%`、反斜线、空格、`# ? ( ) [ ] < > "`，中文原样保留。

`id` 的命名空间是整个 `4-know`，不是单个子目录——`new note x` 之后再 `new adr x` 会造出两个同 id 的文件。审计在至少一侧是决策记录时报冲突；两篇笔记互撞和「改了 `id`」一样属于 schema 契约，由人守。

两份索引都由 `new adr --index` 生成，`new check` 的 `decision_links` 会重新渲染并逐字节比对，手改会被报出来。该命令只允许在完整工作树运行；sparse worktree 缺少未展开目录，不能拿来判定「没有决策」。受控块 marker 缺失、重复或顺序错误时，生成器会在写第一份文件前拒绝运行，避免截断 marker 之后的正文。

### 为什么文件不按项目分散存放

会有一个很自然的念头：体系级的搬去 `0-meta`，项目级的搬进项目目录。放弃了，两个实测理由：

- **跨域的挑不出主人。**现有四条里三条跨域，而它们恰好是最重要的那几条。按路径存就得给它们指派一个错的归属。
- **`0-meta` 没有 frontmatter 契约**，而且是 `strict-ascii`。搬过去等于静默脱离 `id` / `status` / `review` 的约束，而 `id` 稳定性正是跨文档引用的唯一依靠。

所以：文件全留在 `decision/`，归属靠 `scope` 声明，就近可读性靠受控块。

## 做研究

```bash
new research llm-eval
```

生成：

```
research/llm-eval/
├── QUESTION.md      研究问题 + 纳入/排除标准（必须事先写）
├── screening.csv    检索式、数据库、命中数、纳入决策
└── notes/
```

`screening.csv` 的意义：把「我读过一些资料」变成「检索了 3 个库、命中 84 篇、按事先声明的标准纳入 12 篇」。**前者无法复核也无法交接，后者可以。**这是 PRISMA 方法的轻量版。

先写 `QUESTION.md` 再检索，顺序不能反——事后定标准就是在给已有结论找理由。

## 什么时候真的用 Notion

只有一个场景：**要和不用命令行的人共享或协作填写**。那是对外接口，不是事实源。用完把结论沉淀回这里。

不把 Notion 当事实源的三个理由：agent 要 grep 本地文件；决策记录需要 git 历史；导出有损，1 万篇之后迁不出来。
